# نتيجة تطبيق مخطط لوحة المالك على Production

وقت التقرير: 28 أكتوبر 2026، 22:47 بتوقيت الرياض (19:47 UTC).

## التفويض والنطاق

وافق المستخدم صراحة على تطبيق الحزمة التي راجعها وعلى منح حساب Production الحالي المحدد في المحادثة صلاحية مالك المنصة. الموافقة لا تشمل حساباً بديلاً أو تغيير كلمة مرور. لم يحدث دمج في main أو نشر Vercel في هذه الخطوة؛ يلزمان موافقة مستقلة وفق النطاق المعتمد.

المشروع المستهدف حصراً: `ejpzcsfwqziqxwhvqnay` (ZakatFlow Production). لم تتصل هذه الخطوة بقواعد QA ولم تنقل منها بيانات. لم تُستخدم مفاتيح خدمة أو تُعرض بيانات اعتماد.

مصدر الحزمة: الفرع `feature/platform-owner-dashboard-qa`، Commit `9b1e77e358416ed87606b084e3f4ec566dc9d5dc`. طابقت ملفات المراجعة جميع بصمات SHA256SUMS قبل التطبيق. آخر main المرصود بقي `d2178c2a6933001e56165566796caf8b64b5f126`.

## التنفيذ الفعلي

- أُعيد فحص البنية وهوية الحساب المؤكدة النشطة قبل التنفيذ. كان المصدر يحتوي 7 مستخدمين و3 مؤسسات و0 اشتراكات قديمة، ولا جداول منصة أو دوال لوحة متعارضة.
- طُبّق ملف `20261028185536_platform_owner_production_review.sql` عبر Supabase `apply_migration` باسم `platform_owner_production_review`؛ أعادت الأداة success=true وسُجل الإصدار `20261028194521` في سجل الترحيلات.
- استُخدمت الحزمة الكاملة بمعاملتها ومهلها وحراسها كما روجعت، مع إضافة إعداد الموافقة `SET LOCAL yaqeen.platform_owner_ddl_approval` بعد BEGIN فقط. لم يُشغّل db push ولم تُطبّق ترحيلات أخرى من المستودع.
- نجح postflight بعد DDL وقبل التعيين: ستة جداول ذات RLS و12 دالة محمية بإعداد search_path الفارغ والمنح المحددة.
- نُفّذ `provision-owner.psql` بمعاملتي UUID والبريد للحساب الموجود المعتمد، وإعداد موافقة التعيين داخل المعاملة. لم يُنشأ أو يُعدّل حساب Auth. توجد عضوية مالك واحدة مطابقة للموافقة وواقعة تدقيق تعيين واحدة.

اختبار الدور السلبي على الهدف تم داخل معاملة READ ONLY وبـSET LOCAL ROLE ومعرّف اصطناعي غير موجود، وانتهى بـROLLBACK؛ لا إنشاء مستخدم Production اختباري، ولا توقيع JWT أو انتحال تسجيل دخول حقيقي. احتاج فاحص SQL الأول إلى فصل شرط الدور عن استدعاء helper لأن تقييم AND استدعى helper المحظور للمجهول؛ صُحح الفاحص واجتاز جميع الرفضات دون تغيير المخطط أو البيانات.

## مراجعة Supabase Advisors

أُخذ فحص أمني قبل التطبيق وبعده. لم تُمنح anon صلاحية تنفيذ أي دالة جديدة. ظهرت 5 ملاحظات INFO متوقعة لجداول RLS دون سياسات: تمنع المنح جميع القراءات/الكتابات المباشرة عليها ويكون الوصول عبر RPC المحمي فقط. لا تُضاف سياسات عامة لإخفاء الملاحظة.

تظهر 12 ملاحظة WARN للدوال الجديدة SECURITY DEFINER القابلة للتنفيذ بواسطة authenticated. هذا هو مدخل RPC المقصود، ويُراجع مع حارس العضوية والجلسة وsearch_path والمنح واختبارات رفض الدور العادي؛ لا يعني دور authenticated وحده تفويضاً إدارياً.

- تفسير RLS دون سياسة: https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy
- تفسير SECURITY DEFINER لـauthenticated: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable

بقيت ملاحظات سابقة خارج نطاق الترحيل: دالتا purchase guard متاحتان للمجهول و43 دالة SECURITY DEFINER للمستخدم المسجل، وتعطيل فحص كلمات المرور المسربة. لم تُعدّل وظائف النظام القائمة أو إعدادات Auth لمعالجة موضوع مختلف؛ لا ندّعي أن فحص المشروع كله خالٍ من التحذيرات.

## الحالة التالية وحدود الإنجاز

مخطط Production وعضوية المالك جاهزان، والتحصيل المالي ودالتا التعديل لا تزال معطلة. الواجهة المنشورة لم تُحدّث بهذه الخطوة. يلزم تفويض مستقل لدمج الفرع ونشر الواجهة، ثم التحقق من READY وبيئة الاتصال وتسجيل الدخول الفعلي والصفحات على النسخة المنشورة. لا يوجد رابط نشر جديد في هذه الجولة.

خطة تعطيل الوصول الطارئ غير الهدامة في `disable-access.sql` محفوظة ولم تُنفّذ على Production؛ سحب الوصول لا يحذف البيانات. تبقى إزالة سر QA المؤقت من GitHub Actions نقطة تنظيف سابقة لم يُثبت اكتمالها؛ الاختبار المعزول الأحدث لا يستخدمه.
