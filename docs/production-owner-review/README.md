- `../../tests/owner-production-review/`: قاعدة مؤقتة ببيانات اصطناعية واختبارات قابلة للإعادة، مع اعتماد مثبت وملف قفل.

## التوافق ومنع التكرار

الجداول الأصلية `organizations` و`organization_members` و`subscriptions` تبقى دون تغيير. Production يربط مالك المؤسسة وأعضاءها بـprofiles، بينما subscriptions لديه user_id وplan_code وحالات بأحرف كبيرة. لذلك لا يجوز نسخ نموذج QA إليها.

`platform_organizations` امتداد فارغ مفتاحه هو UUID المؤسسة الأصلية مع FK وPRIMARY KEY؛ لا يحتوي نسخاً من الاسم أو البريد أو عدد الأعضاء. دالتا عدد المؤسسات وقائمتها تقرآن organizations والأعضاء الأصليين مباشرة؛ البريد من auth.users عبر هوية المالك. لا تعبئة أولية ولا مزامنة ولا triggers.

`platform_subscriptions` و`platform_plans` نظام جديد يبدأ فارغاً. بناءً على توضيح المالك وفحص Production للقراءة فقط، جدول subscriptions الحالي لا يحتوي أي صفوف (لا سجلات تجريبية أو تقنية مرتبطة بالمستخدمين)، ولا يلزم ترحيل اشتراكات. الصفر هو القيمة الصحيحة في مرحلة التأسيس؛ لا نحذف الجدول الحالي أو نغيّر حسابات المستخدمين أو صلاحياتهم. يُعاد هذا الفحص قبل التطبيق للتأكد من عدم تغيّر الحالة.

التعارض مع أي من الجداول الخمسة الجديدة أو أسماء دوال اللوحة الـ12 تحديداً يوقف المعاملة. جدول platform_admins القديم في المستودع مقبول فقط إذا كان فارغاً وبالشكل المتوقع ودون سياسات غير معروفة. إعادة التطبيق تُرفض بدلاً من استبدال كائنات قائمة. لا تغيّر سجل migrations_history يدوياً؛ يجب اختيار مسار تشغيل ومحاسبة إصدار واحد عند اعتماد الحزمة.

## الحماية والسلوك

- RLS مفعّل على الجداول الستة. الحساب authenticated يقرأ عضويته الخاصة في platform_admins فقط؛ لا منح كتابة مباشرة، ولا قراءة مباشرة للجداول الإدارية الخمسة الأخرى. service_role لا يُستخدم في الاختبارات أو التهيئة ويُسحب منه منح هذه الكائنات الصريحة.
- دالة owner_authorized تتحقق من العضوية المخزنة ومن جلسة auth.sessions مطابقة لـsession_id وUID وغير منتهية، وحساب مؤكّد وغير محظور/محذوف. لا تعتمد على user_metadata أو البريد وحده.
- الدوال الـ11 تتطلب هذا الفحص. جميع الدوال SECURITY DEFINER ذات search_path فارغ وأسماء مؤهّلة بالكامل؛ التنفيذ للأدوار العامة والمجهولة ممنوع. سبب SECURITY DEFINER هو إتاحة قراءات إدارية محمية دون منح المستخدم وصولاً مباشراً إلى auth.users أو الجداول الإدارية.
- دالتا تعديل الباقات وحالة الاشتراك موجودتان بتواقيعهما المتوافقة لكنهما **مقفلتان** حتى للمالك بعد التحقق منه: تعيدان 0A000. الدوال التسع الأخرى للقراءة. لا تحصيل، لا ingestion، لا تمديد فترات، لا إيرادات، لا بيانات بذور.
- قيد مركّب يمنع إسناد دفعة إلى اشتراك مؤسسة أخرى؛ uniqueness لمعرّف مزود الدفع، الأسعار/المبالغ والعملات، ومنع اشتراكين مفتوحين للمؤسسة، وفهارس FK والتواريخ والتدقيق.

## الاختبارات ونتائجها

شغّل محلياً فقط:

```sh
npm ci --prefix tests/owner-production-review
node tests/owner-production-review/run.mjs
```

المحرك PostgreSQL 17.5 داخل PGlite 0.3.14، وProduction المرصود 17.6. القاعدة مؤقتة في الذاكرة وتُغلق بعد الاختبار. أُعيدت أعمدة الجداول ذات الصلة وقيودها المرصودة، مع محاكاة مفاتيح التبعيات profiles/currencies/organization_roles وhelpers المصادقة. **ليست نسخة كاملة من Production ولا خدمة Supabase محلية كاملة**؛ لا Auth HTTP ولا PostgREST ولا JWT توقيع حقيقي في هذه الجولة. فشل تثبيت PostgreSQL النظامي بسبب قيود البيئة ولم تُتجاوز الحماية.

نجحت اختبارات التطبيق الجديد، التوافق مع ترحيل platform_admins السابق، الرفض عند غياب الموافقة أو انحراف المصدر أو إعادة التطبيق، وRLS والمنح، و11 رفض RPC لكل من الدور العادي والمجهول، ومنع القراءة المباشرة والتعيين الذاتي وتزوير metadata، و9 قراءات للمالك، وحجب كتاباته، ورفض جلسة أخرى أو ناقصة أو منتهية أو ملغاة أو مالك محظور. نجحت اختبارات UUID/البريد في التعيين، وقيود FK/التكرار والأسعار، والتراجع الطارئ، والفشل المتأخر داخل DDL مع عدم بقاء جداول جزئية. بقيت صفوف المؤسسات والاشتراكات القديمة الاصطناعية محفوظة. التفاصيل والأعداد في test-result.json.

اختبار RPC السابق على **QA المستضاف الحالي** نجح في GitHub Actions، لكنه كان على مخطط QA القديم؛ لا يحل محل اختبار HTTP على هذه الحزمة المعدلة. لم يُشغّل Supabase Advisor على المحرك المضمّن لأنه غير متاح؛ فُحصت خصائص المنح وRLS وsearch_path عبر كتالوج PostgreSQL محلياً.

## خطة التطبيق المستقبلية — لا تنفيذ الآن

1. مراجعة SQL وهوية المالك وخطة النسخ الاحتياطي/PITR، وتثبيت بصمات الملفات. إعادة preflight ومقارنة البنية؛ التوقف عند أي اختلاف.
2. الحصول على موافقة مستقلة صريحة على DDL لـProduction. التشغيل بواسطة postgres في نافذة صيانة؛ ضبط إعداد الجلسة `yaqeen.platform_owner_ddl_approval=APPROVED_PLATFORM_OWNER_SCHEMA` ثم تنفيذ الملف الكامل. الإعداد حارس ضد التشغيل العرضي وليس بديلاً عن موافقة بشرية.
3. تشغيل postflight. تبقى عضويات المالك والجداول الجديدة فارغة؛ لا تفعيل تلقائي أو نسخ بيانات.
4. موافقة منفصلة على UUID/بريد حساب المالك الموجود. ضبط `yaqeen.platform_owner_enrollment_approval=APPROVED_EXISTING_PRODUCTION_OWNER` وتشغيل provision-owner.psql بمعلمات psql المطلوبة. عدم إضافة حساب بديل.
5. قبل إطلاق الواجهة: إجراء اختبار على Supabase مؤقت كامل بنفس إصدار المخطط، بما فيه دخول حقيقي وPostgREST والجلسات. مراجعة Advisors، وقد حُجبت نماذج التعديل في الواجهة وأُزيلت نصوص QA الثابتة؛ يبقى فحص العرض النهائي قبل النشر.
6. بعد الموافقة على نتائج تلك الجولة، موافقة مستقلة على الدمج والنشر وإعدادات Production النهائية، ثم فحص READY والصفحات والدخول.
7. تشغيل أي مزامنة اشتراكات أو فتح دالتي الكتابة أو التحصيل يحتاج طلباً مستقلاً؛ ليس جزءاً من هذه الحزمة.

## التراجع

قبل COMMIT: أي خطأ يعيد المعاملة كلها؛ عند فشل مهلة القفل نوقف ولا نكرر تلقائياً. لا تغييرات جزئية.

بعد COMMIT: أوقف إصدار الواجهة الجديد أولاً، ثم بموافقة طوارئ اضبط `yaqeen.platform_owner_rollback_approval=APPROVED_DISABLE_PLATFORM_OWNER_ACCESS` وشغّل disable-access.sql؛ اسحب منح الجداول والدوال وأعد تحميل PostgREST. تبقى السجلات والعضويات والتدقيق محفوظة، ولا تمس الاشتراكات الأصلية. تحقق كدور عادي/مجهول من الرفض. لا إسقاط للجداول إذا وجدت بيانات؛ إزالة المخطط لاحقاً تحتاج خطة مستقلة بعد تصدير البيانات وفحص التبعيات. استعادة نسخة كاملة ليست إجراء التراجع الافتراضي لأنها قد تزيل أعمالاً أخرى.

**المخاطر المتبقية:** نجح اختبار Supabase الكامل/HTTP كما في التقرير النهائي. يبقى اختلاف الإصدار الفرعي والتبعيات غير المحاكية، واحتمال تغير subscriptions منذ فحصه الفارغ، والحاجة إلى postflight وAdvisors على الهدف وإعادة فحص البيئة المنشورة بعد الموافقة. لم تُحذف أو تُنقل أي بيانات ولم تتغير Production.
