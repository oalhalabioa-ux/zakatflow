# Private original-enrollment preservation candidate

`services/zatca-private-enrollment-writer.ts` adds an internal `preserveOriginalEnrollment` operation. It preserves the exact original signed public CSR before credentials exist. It is **not an HTTP endpoint, live onboarding coordinator, installed migration, authority submission, signer activation or credential writer**. No production route imports it.

The factory receives a protected deployment-matched Supabase Auth client and a dedicated direct/session-mode `pg` pool. Reader and writer now share `services/zatca-private-session.ts`: SDK `getUser(token)` before checkout, one client per transaction, rollback of unfinished leases, explicit modern/legacy JWT context cleanup, minimal verified transaction-local identity, fixed timeouts/search_path, sanitized errors and disposal of unusable clients. The existing 38 reader regressions still pass after this extraction. Dedicated pool/TLS/scoped private-role provisioning remains required; transaction-mode pooler cleanup is not certified.

## Inputs and authorization

The target is strictly company, environment and saved connection. The **internal coordinator's** original material is strictly enrollment UUID, exact original CSR PEM, immutable KMS key ARN, public SPKI and requester email. No role, actor, expected identity, certificate, SQL or database configuration is accepted. Inputs/dependencies are captured before asynchronous Auth. These fields must not be passed straight through from HTTP JSON: the future coordinator must obtain and validate fresh KMS metadata itself. A mathematically valid public CSR does not prove AWS key ownership.

The writer locks current active OWNER/ADMIN membership, then the saved scoped connection with `FOR UPDATE`. It derives every unit identity field from that locked connection, requires the exact saved KMS key reference, and checks the original PKCS#10 signature, canonical DER/base64/SPKI, secp256k1, SHA256, exact saved SAN/subject identity, current application profile and environment template using the extracted `inspectZatcaOriginalCsr` primitive. The existing certificate verifier uses those same CSR checks. Native/cloud calls never run while these database locks are held; CSR inspection is local synchronous work with bounded input.

Only then does it call the private INVOKER `begin_initial_enrollment` candidate on the same client/transaction. SQL rechecks current authorization/state and immutable original-request consistency. The returned checksum, original CSR, operation/scope/complete saved identity and first actor/time are checked before COMMIT. Any inconsistent response rolls back the insert. The returned internal receipt contains only stage `ORIGINAL_ENROLLMENT_PRESERVED_ONLY`, enrollment ID/digest and original actor/time. It grants no signing/activation authority and contains no CSR, requester email, private key, credential or token.

## Exact retries and uncertain outcomes

Reuse the **same enrollment UUID and byte-identical original CSR/public key/email** on retry. A new UUID or regenerated CSR is not a retry. Exact retries preserve the first record/actor/time, even when another currently authorized company admin retries or credentials subsequently appear. A different operation/request cannot replace that record; a connection already onboarded without original provenance cannot be backfilled.

COMMIT may have succeeded even if its acknowledgement, subsequent context cleanup or pool release fails. The writer returns no success receipt in those cases and discards the unusable connection; it cannot undo an already committed transaction. The future coordinator must reconcile by retrying this exact original immutable operation. It must not regenerate material, invent an identifier, automatically resubmit to the authority or claim that a client error proves rollback. SQL execution errors are sanitized, except an exact allowlist of `P0001` private-contract denials after rollback. No raw diagnostics/cause are returned.
