# Original-enrollment dispatch preparation and durable fence

`services/zatca-private-enrollment-coordinator.ts` joins the private saved-original reader, original CSR inspection and separately reauthorized durable intent claim. `services/zatca-private-enrollment-dispatch.ts` adapts the owner-only INVOKER contract in `tests/fixtures/zatca-enrollment-dispatch.sql`. These are isolated preparation components: **no live HTTP/authority/AWS transport, OTP handling, response/secret staging, activation, installed migration or production caller**. Existing onboarding remains unchanged.

## Local preparation flow

The coordinator accepts a strict saved company/environment/connection and stable original enrollment/dispatch UUIDs. It rejects CSR, OTP, digest, role, URL and retry/force overrides. It loads the preserved request using verified Auth, checks the requested original enrollment UUID, verifies the actual signed CSR against its saved complete identity/public key, then derives the digest from storage and invokes the fence. Inputs and dependencies are captured before async work. No company/requester/CSR data is returned; unexpected internal errors are replaced by a fixed code.

The claim uses a fresh SDK `getUser(token)` call and the shared private session helper. Its private SQL function locks current active OWNER/ADMIN membership and the scoped connection, loads the exact original request, recomputes its checksum, compares the saved digest and current unit stamp, and checks KEY_READY/no credentials/no registry for a first claim. It never treats a previous read as current write authorization. SQL checks consistency, not cryptography or AWS ownership.

There is one immutable `INTENT_RECORDED` row per original enrollment, with a unique dispatch UUID, original digest, first actor and database time. No payload, OTP, secret, certificate or error text is stored. RLS is enabled; PUBLIC/anon/authenticated/service_role table and function grants are revoked, including explicit default grants reproduced by disposable QA. The function is INVOKER, with fixed pg_catalog search_path. The future scoped private role/pool/TLS/migration still need provisioning/review.

## Non-duplication and ambiguity

- The first insertion returns `FIRST_INTENT_RECORDED` **only after** receipt validation, acknowledged COMMIT and successful connection cleanup. The coordinator labels the result `ENROLLMENT_COORDINATION_PREPARATION_ONLY`. This is a local record, not evidence that anything was sent or approved, and not a reusable transport capability.
- Exact replay returns `RECONCILIATION_REQUIRED`, preserving the first actor/time. Another active company admin may reconcile that same operation. A changed dispatch UUID is denied; it cannot reset or reacquire the existing intent. Current membership/unit/digest checks still apply to every replay.
- Concurrent claims serialize under the connection lock and unique original-enrollment constraint. The tests show exactly one first-intent result; other exact calls require reconciliation. This is **not exactly-once remote delivery**. No remote call exists in these components.
- A crash before COMMIT leaves no committed intent. A crash/lost acknowledgement after COMMIT, failed cleanup or an interrupted process after recording the intent may leave a durable intent without any remote submission. Replay still requires reconciliation. The same IDs must be preserved; never infer rollback from a client exception.
- There is no TTL, reset, timeout reclaim, delete or automatic resend. An uncertain attempt deliberately stays blocked until a future authorized recovery/reconciliation flow establishes what occurred. Neither changing IDs nor regenerating the CSR is recovery.
- Receipt scope/operation/digest/state and first actor are checked before COMMIT. Corrupted receipts roll back new inserts. Known exact P0001 denials may cross the private adapter; raw SQL/connection/cleanup diagnostics and causes do not.

The protected future transport must consume a newly committed first intent at most once in its own control flow, recheck other prerequisites close to dispatch, preserve observed responses/immutable secret versions safely, and record an audited outcome. It must never replay a saved first-intent JSON result to send again. AWS key ownership, CA/profile/trust freshness and authority authentication remain independent gates; CSR consistency and this local fence do not establish them.

## Validation — 2026-10-25

New coverage consists of **16 disposable SQL**, **36 private adapter unit**, **7 real pg adapter** and **13 coordinator unit** tests (72 cases; overlapping broader suites are separate). SQL tests use synthetic public CSR bytes as persistence fixtures. Coordinator unit tests use real locally signed Arabic CSRs with mocked storage adapters. Actual pg/Auth-server transport to Supabase QA and authority acceptance are not claimed.

Coverage includes 16 simultaneous exact claims with one first result, competing dispatch IDs, first actor/time, exact retry by another admin, missing/revoked/cross-scope permission, changed unit/digest, checksum corruption, no first claim after credentials, immutable rows, rollback-before-commit, RLS/INVOKER/explicit application grants, inconsistent receipt rollback, current revocation while waiting, and clean modern/legacy pooled identity. Real PostgreSQL COMMIT/cleanup acknowledgement loss is injected after actual successful commits; replay cannot reacquire. This is not a real network-fault test.

The native relational enrollment case now performs private original preservation → saved read/CSR/certificate/CRL checks → coordinator preparation/first intent → replay requiring reconciliation → enrollment-aware registry/reservation/finalization. Its final XML storage payload is synthetic; signed UBL is verified separately by XAdES tests. The native relational suite is **147/147**, including the seven pg adapter cases. Existing SQL suites remain 17 ledger, 30 source, 22 registry, 18 enrollment and 8 permission tests. TypeScript passes. The full focused native suite adds the 49 unit cases to its prior 381; SQL-only cases are run separately with opt-ins.
