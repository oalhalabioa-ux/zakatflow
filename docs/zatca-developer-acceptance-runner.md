# Repeatable Developer Portal acceptance diagnostic

Scope: the existing `yaqeen-fatoora-qa` Vercel Preview project and existing scoped KMS key only. This runner is outside application routes, never reads a database, never creates keys/secrets, and never uses the real FATOORA production or Simulation namespace. Its only network destinations are the existing AWS credential/signing services and the fixed authority `/e-invoicing/developer-portal` test API. No automatic HTTP retries are performed.

The runner explicitly requires `--developer-only`, Preview, the exact QA role/key/region, and the exact Vercel issuer/audience/project claims before cloud work. STS verifies the token through the credential provider. It checks KMS metadata and the compliance certificate's actual SPKI against that key. A fresh synthetic CSR uses the documented Developer Portal OTP example, not a real taxpayer OTP. Credentials remain in memory; neither credentials, CSR/certificate, invoice XML nor raw authority messages are published.

Six synthetic scenarios use the strict application UBL builder: standard and simplified invoice, credit note and debit note. Counters and previous hashes form one diagnostic chain. Each result requires HTTP 200, explicit validation PASS, zero errors and zero warnings. A missing or malformed validation response fails closed. The standalone simplified SDK 3.4.5 helper remains synthetic-only; its known signed-properties limitation is not repaired or promoted by this diagnostic.

After all six compliance checks pass, the runner requests the Developer Portal's test `/production/csids` resource. This path is **inside the developer-portal namespace**, not the production environment. Its certificate must match the same key before reporting or clearance is attempted. An unrelated sample certificate blocks both operations. The runner then builds six **fresh** delivery documents: new UUIDs and counters 7–12 continue the diagnostic previous-hash chain. Simplified delivery documents use the returned permanent test certificate in their XML certificate, certificate digest and QR issuer-signature field; they are signed again with the same checked QA key. The already-signed compliance samples are never patched or replayed for delivery. Standard delivery documents remain unsigned and without a locally generated QR, pending authority clearance.

Reporting requires an explicit REPORTED result and clearance an explicit CLEARED result, separately from validation status. All six unique document/route pairs must pass: missing, duplicate, misrouted, rejected or warning-bearing results cannot finish the diagnostic. Only then is diagnosticPassed=true; releaseReady stays false. Nothing activates an application connection or updates an invoice.

The only published file is `public/acceptance.json`, containing stage, safe rule codes and per-scenario outcomes. `releaseReady` is always false: current official SDK/profile verification, complete certificate identity/trust/revocation and authorized-organization FATOORA Simulation remain separate gates. This diagnostic cannot certify production compliance.

Unit checks cover environment/project/key guards, HTTP-versus-business acceptance, reporting/clearance dispositions, redaction, warning refusal, malformed certificates and actual key mismatch across supported certificate envelopes. Prior passing cryptography/storage checks are retained; no financial source code or schemas are modified.

## Certificate handoff regression — 2026-11-19

Review of the authority's [integration instructions](https://zatca1.discourse.group/t/integration-with-zatca/3045), specifically the separate CCSID and PCSID signing instructions, exposed a latent error: the former runner retained the six compliance payloads and reused them after obtaining the permanent certificate. This would still embed CCSID in simplified reporting even if the permanent certificate matched the same public key. The last hosted run stopped earlier on the unrelated permanent certificate; it never exercised this faulty later path.

`tests/zatca-developer-certificate-handoff.test.ts` now exercises the actual runner with real local secp256k1 signatures and two distinct leaf certificates for the **same** key. AWS, STS, authority HTTP and report-file writes are mocked; these are local regression tests, not hosted or authority acceptance. The original implementation failed the regression by replaying only six UUIDs across twelve requests. After the fix, independent checks require twelve unique UUIDs, counters 1–12, the exact previous-hash chain, actual XML/payload hashes, correct phase authorization, PCSID certificate/QR binding, and valid invoice signatures. Negative cases retain the key-mismatch stop, compliance-warning stop, reporting-warning failure and the no-cloud-work production guard. Synthetic private keys are removed with the test fixture directory.

The follow-up does not change the runtime signature profile, relax certificate-key checks, add Simulation endpoints or accept tenant credentials. No hosted rerun is justified solely by this correction while the known Developer Portal certificate mismatch remains. Authorized Simulation access and the unresolved runtime SDK/security-profile difference are still separate acceptance requirements.
