# ZATCA Phase 2 preparation — 2026-10-22

Original preparation base: `906495d1`; synchronized with main `998f0837` on 2026-10-24 while retaining its newer Next.js/Zod/Vitest/Vite versions. This branch is preparation work, not a complete Phase 2 integration or production release.

## Implemented in this branch

- Pure unsigned UBL Invoice XML preparation for standard/simplified invoices, credit notes and debit notes (388/381/383 and 0100000/0200000).
- Reuses the existing Decimal invoice calculation; line discounts remain line allowances and are not deducted again at document level. Group VAT rounding stays consistent with existing saved totals.
- Preserves source currency, separate SAR VAT total, supplied UUID, invoice counter and previous hash. It does not allocate, increment or fabricate chain state.
- Explicit supplier registration identifier, supply date and payment method; buyer identifier required for standard invoices; actual original invoice number and reason required for notes.
- Rejects XML-invalid characters, unsupported top-level inputs (including prepaid amounts), missing exemption reasons, mixed outside-scope categories and conflicting grouped exemption reasons. Existing workflows and financial writers are untouched.
- Isolated AWS KMS signing primitive: accepts an immutable key ARN and the expected certificate public key, verifies secp256k1/key usage/algorithm and exact key matching, hashes caller-supplied canonical SignedInfo once, requests `DIGEST` signing, converts strict DER ECDSA into XMLDSig r||s, and independently verifies every returned signature before returning it. No HTTP endpoint or production import is added.
- Certificate preflight: exactly one PEM or canonical base64 DER certificate, pinned to the authorized EGS unit's stored SHA-256 fingerprint; rejects malformed/trailing/bundled input, expired/not-yet-valid certificates, CA signers and incompatible key curves. Extracts exact certificate DER, raw SHA-256 certificate digest, decimal serial and public SPKI. This does not establish certificate trust, identity, profile/key-usage conformity or revocation status.
- Invoice reference hash preparation: pinned `libxml2-wasm` 0.7.1 for native libxml2 Canonical XML 1.1 without comments after namespace-aware exclusions of UBLExtensions, cac:Signature and QR document references. Rejects DTD/entity declarations, processing instructions, XML 1.1/non-UTF-8 declarations, unknown namespace prefixes, wrong/nested invoice roots and oversized input. Preserves significant whitespace and does not normalize/reformat financial content.
- XAdES signed XML preparation: builds only from the strict existing draft/context builder; includes the UBL extension/signature metadata, two explicit C14N 1.1 references, SignedProperties with time, SigningCertificateV2 digests through supplied root, explicit configured policy identifier/digest and DataObjectFormat. Checks supplied issuer linkage/signatures/dates/CA flags and root self-signature (not a full trust decision). Accepts a signing callback compatible with the AWS primitive, verifies its raw ECDSA result, then checks final document/reference canonical bytes again. Output remains `SIGNED_XML_PREPARATION_ONLY` with no authority status; simplified QR is opt-in as described below.
- Follow-up: opt-in experimental simplified QR preparation, with nine TLV fields and binary hash/signature/SPKI/certificate-signature values. Extracts the certificate outer ECDSA signature from bounded DER, checks UTF8 field lengths and the 700-character limit, validates monetary strings exactly and preserves source-currency VAT. `includeSimplifiedQr` attaches the QR before signature metadata without changing either signed reference. Standard QR requests fail before signing and remain reserved for clearance. Output still has preparation-only status; current SDK tag 7/8/9 encoding interoperability and full certificate validation remain gates.

- Isolated PostgreSQL ledger storage contract in `tests/fixtures/zatca-phase2-ledger.sql`: per-organization/environment/unit row locking, one durable pending reservation, immutable document/UUID/snapshot identity, idempotent exact-artifact finalization and atomic artifact/head updates. This is a disposable QA fixture, **not a Supabase migration or enabled application ledger**. No role is granted access, no caller exists, and `PREPARED` never means issued or accepted. See `docs/zatca-phase2-ledger-contract.md` for the remaining authorization/cryptographic binding/recovery gates.

- Reservation binding preparation: `createZatcaPreparationSnapshot` validates a versioned saved-document DTO, ordered saved line amounts and all six saved totals using existing Decimal calculations, including source currency/FX. `prepareReservedZatcaArtifact` rechecks scope/snapshot and derives UUID/counter/PIH only from a freshly loaded trusted reservation, preserves bigint counter text, builds/signs from that snapshot and compares independently recomputed invoice hashes before returning private finalization arguments. It creates no endpoint, database adapter, migration or production writer. PostgreSQL snapshot digest remains a trusted storage value, not a JS-computed proof of snapshot authenticity.

- Read-only session/access preflight: `services/zatca-phase2-access.ts` uses existing `requireUser` (server `auth.getUser`) and active OWNER/ADMIN membership from the database before reading document metadata. It derives connection identity from the saved DRAFT, checks company/environment, readiness, seller VAT and supported invoice category, and reads no keys/certificates/secrets. Current one-connection/EGS-per-company/environment schema uses that saved connection primary key as unit identity. No browser-supplied user/connection/unit is accepted. This is **ACCESS_CHECK_ONLY**, not a frozen snapshot, authorization token, write adapter or reservation endpoint. Permissions/identity must be rechecked in the future atomic source-freeze/reserve transaction.

- Atomic source-freeze candidate, isolated under `tests/fixtures/`: `reserve_saved` rechecks session subject/current membership and connection under locks, reconstructs the versioned snapshot from saved relational header/lines/context and compares the prevalidated expected snapshot before allocation. Guards freeze header/children/context and touch parent metadata to reject stale REPEATABLE READ in either direction. Source/permission race tests and an actual relational snapshot → signed artifact/finalization test are included. This is still a disposable owner-only SQL candidate, **not an installed Supabase migration or production authorization path**. Its auth stub/harness must never be deployed; real RLS/privileges, lifecycle writers, linked accounting, recovery and batch performance remain gates described in the ledger contract.

## Integration boundary

`buildUnsignedZatcaXml` is not imported by any production route. Its output is labelled `UNSIGNED_PREPARATION`; it contains no signature or issuance QR. It must not be submitted or used to mark a document ISSUED/CLEARED/REPORTED. The current Phase 1 issuing flow is unchanged.

Supported preparation scope follows the existing domestic invoice DTO. Exports, advance-payment adjustments, document charges, self-billing and other special transaction indicators are not implemented. They require explicit models and acceptance tests before support is claimed. Invoice unit codes and exemption identifiers still require ZATCA SDK/business-rule validation.

`createZatcaKmsSigner` is a server-side primitive only. It does not canonicalize XML, validate certificate trust/expiry/revocation, construct XAdES or authorize tenants. Its caller must load the correct unit and certificate under authorization, supply the certificate's SPKI and canonical SignedInfo, and verify references. It must never be exposed as a generic signing endpoint. Its successful result does not mean an invoice is signed or accepted end to end.

`inspectZatcaSigningCertificate`, `prepareZatcaInvoiceHash`, QR preparation and `prepareSignedZatcaXml` are also not imported by production routes. Certificate pins must come from saved, authorized unit onboarding, not client-supplied pins. Do not treat preflight or supplied chain linkage as a trust decision: environment-specific configured trust anchors, full certificate path/profile/key usage, VAT/EGS identity binding and fresh revocation checks remain mandatory. The supplied root and policy are not automatically trusted. Recheck time/revocation at actual signing and use a trusted server clock. Hash preparation must run on the final document namespace context; adding/moving namespace declarations or pretty-printing afterwards can invalidate reference hashes. Optional simplified QR assumes the application's existing Riyadh issue-time convention (+03:00) and remains experimental until profile validation. Runtime packaging of the WASM asset still requires testing when the module is wired into an actual backend deployment.
