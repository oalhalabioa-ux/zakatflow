# استيضاح فني جاهز للمراجعة — لم يُرسل

الموضوع: مواءمة Java SDK 3.4.8 مع مواصفة الخصائص الأمنية v1.2 لتوقيع الفواتير المبسطة

مرحبًا فريق دعم الفوترة الإلكترونية،

نطور حلًا للفوترة الإلكترونية، واختبرنا حزمة Java SDK 3.4.8 المنزلة عبر بوابة المطورين باستخدام Java11 وفواتير ومفاتيح وشهادات مصطنعة فقط. نجحت حالات XML القياسية وحساب بصمة الفاتورة. نرجو توضيح المسار المعتمد للفواتير المبسطة في النقاط التالية:

1. الصفحات19–22 من مواصفة الخصائص الأمنية v1.2 المنشورة بتاريخ2023-05-19 تصف توقيع SignedInfo وربط SignedProperties به، وتطلب SigningCertificateV2. مخطط UBL-XAdESv132-2.1.xsd ضمن الحزمة يرفض SigningCertificateV2 ويتوقع SigningCertificate. هل توجد نسخة مخطط/إعداد أو مواصفة أحدث معتمدة تعالج هذا الاختلاف؟
2. النموذج المتوافق مع دليل Signing Process وSDK يوقّع بصمة الفاتورة. في اختبار محلي مصطنع، قبِل SDK تغيير SigningTime وإعادة حساب بصمة الخصائص دون إعادة توقيع. في المقابل، توقيع SignedInfo الذي يربط خصائصه يُرفض. كيف ننتج نموذجًا يجمع سلامة ربط الخصائص والقبول لدى SDK وبيئة المحاكاة؟ هذه نتيجة محلية للنموذج التجريبي وليست بلاغًا عن خلل في بوابة الهيئة.
3. الصفحة25 من المواصفة تحدد32 بايت لقيمة حقل QR6، بينما يقبل النموذج التجريبي في SDK نص Base64 للبصمة داخل الحقل. ما التمثيل المعتمد لحقل6 وحقل7 في المحاكاة والإنتاج؟

صححنا بالفعل وقت QR ليطابق IssueDate/IssueTime في XML، واختفى تحذير timeStamp في الحالات الثلاث. لم نعدّل قواعد SDK أو نعطّل التحقق من الشهادة/المفتاح، ولم نفعّل الربط على الإنتاج.

نرجو الإشارة إلى المواصفة والنموذج وإعداد SDK المعتمدة قبل استكمال اختبارات الإبلاغ والاعتماد في المحاكاة. يمكن توفير ملفات مصطنعة قابلة لإعادة الاختبار دون أية مفاتيح خاصة أو بيانات عملاء.

شكرًا لكم.
