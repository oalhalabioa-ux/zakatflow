# Verified private PostgreSQL enrollment read boundary — 2026-10-25

`services/zatca-private-enrollment-reader.ts` adds `createVerifiedZatcaEnrollmentReader(auth, pool).loadOriginalEnrollment(accessToken, target)`. It uses the actual Supabase SDK `getUser(token)` contract and a dedicated node-postgres client to read the original private enrollment. It has **no live caller, HTTP endpoint, pool/credential provisioning, business write, AWS call or deployment**. It returns `AUTHORIZED_ENROLLMENT_READ_ONLY`, an internal read result, not an issuance/activation authority or transferable permission grant.

## Identity and tenant boundary

The target accepts only organization ID, connection ID and environment. User/role/enrollment ID/SQL/CSR/certificate overrides are rejected before authentication. Token text is bounded, is not decoded locally and is never copied into SQL/session claims or errors. The injected Auth client must be initialized by trusted deployment code for the intended Supabase project. `getUser` must return a valid authenticated UUID/audience and a non-anonymous user. Caller user_metadata does not authorize anything.

Only after Auth succeeds does the reader acquire a private pool client. Inside that single transaction it locks current active OWNER/ADMIN membership, then the company's exact saved connection. Original enrollment is loaded by all three scope fields. It validates returned row/saved-identity scope, current unit stamp, immutable enrollment payload checksum and canonical CSR bytes/digest before reconstructing the original PEM. No fresh CSR/signature is generated. The saved-unit schema is shared with the native identity verifier.

Returned CSR and saved identity contain internal company/requester data. They must stay inside the trusted backend; do not serialize this result directly as an API response. The native verifier, fresh KMS metadata and the enrollment-aware SQL writer still need to run before any write/activation, with fresh authorization. The native relational test now preserves the original through the private writer, then feeds the reader's actual saved request/identity into the composite verifier before registry/reservation/finalization consistency checks.

## Connection ownership and cleanup

Use a **dedicated direct PostgreSQL or session-mode pool**, with verified TLS/certificate configuration, bounded pool size/timeouts, a reviewed private DB role and an idle-pool error handler that emits sanitized operational codes. The fixture currently uses the SQL owner as a backend stand-in; deployment role grants/ownership/RLS are not provisioned or certified by this module. App anon/authenticated/service_role credentials cannot access the private contracts and must not be used as a workaround.

This implementation does not create a pool or accept a connection string from a request. In particular, it does not claim its session cleanup is verified on a transaction-mode external pooler: outside-transaction cleanup statements can be dispatched to another physical backend there. Choose/review the connection mode before wiring a production pool. Do not use an arbitrary shared application pool or a browser/REST schema exposure.

The reader leases exactly one client. It rolls back any unfinished transaction left on that client and clears stale global subject/claims, legacy JWT JSON, role and email, starts a transaction, sets fixed local search path/lock/statement/idle limits, and sets **transaction-local** subject/minimal claims derived only from the verified actor. Core setters are schema-qualified even before the local search path is applied. Legacy single-JWT/email fields are cleared and the legacy role is fixed to authenticated, so they cannot override the verified minimal claims. Membership/connection row locks keep authorization/configuration consistent during the read. All statements use that same client with parameterized scope values. SQL writes to company data are absent; session identity is the only state being set.

Success commits, then clears session context before release. Known authorization/integrity denials roll back and clean the client. Unknown query/connection errors or failed rollback cause the client to be discarded. Failed final cleanup/commit/release returns no private read result; failed release also attempts to close the client. A checked-out-client error listener prevents native error events from escaping and is removed after release/close. Original native messages, SQL diagnostics, connection strings, tokens and causes are not returned.

SQL limits are 2-second lock timeout, 5-second statement timeout and 10-second idle-in-transaction timeout. Authentication happens before connection acquisition; native verification/cloud work happens **after this short read transaction**, not while its locks are held. The private initial-request writer and any later activation writer must perform their own fresh locked authorization rather than relying on this earlier read. The reader/writer now share the verified-session implementation in `services/zatca-private-session.ts`.
